# 「隔壁」项目介绍视频逐字稿

预计时长：4 分 40 秒至 5 分钟。方括号内为录屏操作提示，不需要念出。请按实际可运行的界面展示对应步骤。

## 0:00–0:20 开场

业主群里的东西沉得太快，真正需要的人常常还没看到，物品就被刷走了。我做了「隔壁」——让闲置在沉没之前被看到。它像一块数字楼道公告板，服务邻里之间的转赠和自提。

## 0:20–1:40 Demo 主流程

[展示首页卡片流]

首页先展示在售物品。卡片上的新鲜度分成三档，让住户先看到刚发布的东西；交易方式和发布者房号也放在卡片上，扫一眼就能判断要不要继续看。现在我选择只看免费的，再输入关键词搜索，列表会按筛选条件更新。

[筛选免费，搜索物品，进入详情]

点进详情，可以查看完整描述、发布者、想要人数和留言。感兴趣时点“想要”，发布者能知道谁有意向；也可以在留言板里询问物品情况。

[点想要并添加一条留言]

如果我手上也有闲置，可以从发布入口填写名称、描述和交易方式。发布后回到物品列表，就能看到这条新信息。

[发布物品并回到详情]

物品送出后，发布者把它标记为已送出，卡片进入归档状态。最后看一下数据看板，可以了解本月发布和送出的数量、当前在售数，以及最快被领走和最受关注的物品。

[标记物品已送出，再打开看板]

## 1:40–2:40 LLM 三件套

[打开一件标价物品的定价建议]

第一项是定价建议。填写物品名称和状态后，系统给出一个参考区间，帮助发布者快速确定价格。它只是建议，最终价格仍由住户决定。

[展示文案优化]

第二项是文案优化。它会把简短描述整理得更清楚，用户可以查看后再决定是否采用，不会自动覆盖输入内容。

[打开 FAQ 并点击“还在吗？”]

第三项是常见问题回复。这里我把数据库里的真实物品信息注入提示词，所以回答“还在吗”时能结合物品当前状态作答。这是一次最小化的 RAG：先检索相关记录，再把上下文交给模型生成回答。模型服务不可用时会返回规则兜底，不让这个功能阻断主流程。

## 2:40–3:40 架构与 ER 图

[展示架构图和 ER 图]

前端使用 React、Vite 和 TypeScript，页面请求通过 Vite 代理转发到 FastAPI；后端用 SQLAlchemy 访问 SQLite。数据库按业务拆成四张表：users 保存住户，items 保存闲置物品和送出信息，wants 保存想要关系，messages 保存留言。

这里有四条关键 CHECK。第一，只有标价物品可以有价格，标价就必须填价格。第二，物品状态和送出时间必须同时成立。第三，送出时间不能早于发布时间。第四，只有已送出的物品才能指定接收人。把这些规则放在数据库层，即使请求绕过前端校验，数据仍然要保持自洽。

## 3:40–4:40 功能取舍与决策

这个版本主动砍掉了一些功能。首先不做登录密码：这是熟人小区场景，输入姓名就能进入，把时间留给发布、浏览和交流。其次不做图片上传：当前用标题对应的品类占位图，已经足够帮助识别物品。数据量有限，所以不做分页；也不做编辑、删除和撤销送出，让物品状态只从在售走向已送出，减少复杂分支。实时推送也暂时不做。

我还把原本可能独立的 trades 表折叠进 items，因为一件物品最多送出一次，拆表会增加关联查询和状态不一致的机会；同一行也能直接约束成交时间。后端统一用同步接口，避免同步模型调用阻塞事件循环。前端没有引入 shadcn/ui 或请求缓存框架，页面所需的表单和卡片用 Tailwind 与 React 完成，依赖少，出了问题更容易定位，也更容易解释。

## 4:40–5:00 收尾

这次开发让我更明确：做产品不只是把功能加上去，也要根据场景和时间判断哪些事情值得做。后续可以再接入真实登录、成交流水和消息推送，但核心仍然是让邻居之间的闲置及时被看到。
